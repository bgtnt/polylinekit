# PolylineKit 0.1.0-alpha.1

**Status: published on NuGet.org on 2026-10-10:**
[Core](https://www.nuget.org/packages/PolylineKit.Core/0.1.0-alpha.1) and
[optional Clipper adapter](https://www.nuget.org/packages/PolylineKit.Clipper/0.1.0-alpha.1).
The [GitHub prerelease](https://github.com/bgtnt/polylinekit/releases/tag/v0.1.0-alpha.1)
preserves the verified original packages and measurement evidence.
The release provides numeric area and region overlap for .NET, with a
dependency-free core and an optional Clipper2 adapter for quantized comparisons
and output contours. There is no new claim of speed for these package binaries.

## Choose a package

| Package | Use | Assemblies and dependencies |
|---|---|---|
| `PolylineKit.Core` | Filled area, intersection, region comparison, prepared ring collections, normalization, sampling and alignment | `PolylineKit.Winding.dll`; no external runtime libraries |
| `PolylineKit.Clipper` | Existing decimal-grid comparisons and resolved output contours | `PolylineKit.dll`; Core and Clipper2 2.0.0 |

Both packages contain `netstandard2.0` and `net10.0` assemblies, XML API
documentation, their own README, the MIT license and repository metadata.
The package IDs describe their roles; historical assembly identities are
preserved for binary compatibility. Public types remain in `PolylineKit`.
Deploy the resolved dependency graph, not an isolated replacement DLL.

Delivered source: `a07ac5528da4cd0fc00c29d9bff01fae4d76c031`, pinned by
`v0.1.0-alpha.1`. The [release assets](https://github.com/bgtnt/polylinekit/releases/tag/v0.1.0-alpha.1)
include both verified `.nupkg` files, `verification.json`, two evidence archives
with generation metadata, and `SHA256SUMS`. All eight assets were downloaded
without authentication and matched their SHA-256 values. Later documentation
updates on `main` do not replace these binaries or their source identity.

NuGet publication used the already verified GitHub files, without rebuilding.
Repository signing changes their outer ZIP bytes; package contents and assemblies
remain those of the delivered source. Follow the
[installation and verification guide](../releasing.md) and run the
[coverage example](../../examples/PackageCoverage). Its nonconvex L-shaped zone
has area 20, the footprint has area 16, and their intersection is 7. Coverage is

## Delivery verification

The [NuGet publication workflow](https://github.com/bgtnt/polylinekit/actions/runs/38074576526)
pushed the verified pair through Trusted Publishing. Both public downloads were
then compared with the GitHub originals: all ten original entries in each package
are byte-identical; only the repository signature was added. `dotnet nuget verify
--all` passed for both packages. Four fresh consumers restored exclusively from
NuGet.org and passed the contracts below on .NET 8 and .NET 10, including the
prepared shell/hole/island and empty-region cases. Their loaded assembly hashes
match the delivered source; Core-only restore brings no third-party packages.

`scripts/verify-packages.ps1` packs Release binaries from a committed checkout,
inspects both actual `.nupkg` files, and restores four consumers outside the
repository, using only `PackageReference`:

| Consumer | Selected library assets | Contract |
|---|---|---|
| Core / .NET 10 | `net10.0` | Coverage, region comparison, prepared shell/hole/island, empty regions and transformation; no adapter or Clipper |
| Core / .NET 8 | `netstandard2.0` | Same Core contracts |
| Clipper / .NET 10 | `net10.0` | Core types plus quantized comparison and output contours |
| Clipper / .NET 8 | `netstandard2.0` | Same adapter contracts |

The verifier isolates NuGet caches and maps `PolylineKit.*` to the produced
local feed. It checks `project.assets.json`, restored package bytes, selected
assembly target attributes and runtime references. Running portable assets under
.NET 8 is not a .NET Framework test. CI repeats the package check on Windows
and Linux, alongside the existing correctness and legacy-consumer checks.

The generated `verification.json` records the exact source commit, package
SHA-256 values and consumer outcomes. It accompanies the local package pair;
publishing a different rebuild requires a fresh verification record.

The release includes `PreparedRegion.FromRings` and `RegionArea`.
All four external consumers check a shell, an oppositely oriented hole and a
separate island under NonZero and EvenOdd: areas 88 and 64, intersection 40,
union 112, XOR 72, IoU 5/14 and Jaccard distance 9/14. Empty regions return zero
areas and undefined overlap ratios. See the [multi-ring guide](../regions.md).
The release tag and verification record identify the delivered source; earlier
locally built candidates predate the multi-ring API.

## Limits and evaluation scope

- Coordinates are planar. There is no geographic projection or geodesic area.
- `PolylineArea` accepts one implicitly closed ordered walk per operand.
  `PreparedRegion` and `RegionArea` also accept multiple independently closed
  rings, including holes, disconnected components and empty regions. Rings
  contribute to one winding field: NonZero holes require deliberate opposite
  orientation; EvenOdd applies parity. The library does not infer hole roles,
  reverse rings or union independently filled polygons automatically.
- `double` areas and intersection coordinates can lose precision, even when
  geometric predicates are exact. Read the [input and numerical contract](../area.md).
- Overlapping footprints' individual coverages cannot simply be added to obtain
  union coverage. A trusted simple ring's own area is cheaply computed by shoelace.
- The general engine retains at most 4 MiB of array payload per thread. The
  separate .NET 10 integer engine can retain another 4 MiB. These are cache
  limits, not a peak-memory cap. Large repeated inputs can allocate again.
  See [memory behavior](../performance.md).
- The adapter quantizes coordinates and uses Clipper2 even when contours are
  not requested. Core area calls do not load it.
